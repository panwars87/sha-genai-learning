SECTION 1

What an LLM call is

Explain like I'm 10

An LLM is a super-autocomplete. It reads your words as small pieces called tokens and guesses the next piece, then the next, until the answer is done. It forgets everything the moment it finishes.

Every LLM feature, however clever it looks, is one request: a list of messages goes in, one message comes out. The system message sets the rules. The user message carries the task. The reply comes back as an assistant message, with token counts and a finish_reason that says whether the model finished (stop) or was cut off (length).

The script makes this call bare, through LiteLLM: a library that speaks one format to every vendor. It names one vendor's model in the code, anthropic/claude-haiku-5-5. Notice what's missing: no limit on spend, and switching vendor means editing code. Module 2 fixes both.

Current models think before they answer. The thinking is billed as output tokens and counts toward the output limit, even though you never see it.

SECTION 2

Tokens and cost

Explain like I'm 10

The model doesn't read letters or words. It reads chunks, roughly three-quarters of a word each, and every chunk in and out has a price, like a taxi meter.

Tokens are the unit of everything: cost, speed and limits. English averages about four characters per token. Numbers, codes like INV-1001 and other languages break into more pieces, so they cost more per character. Output tokens cost about five times input tokens, so long answers are the expensive part.

A worked example

Summarize INV-1001Tokensfast (Haiku 5.5)smart (Sonnet 5.5)
Input: prompt + invoice≈ 420$0.000042$0.000840
Output: thinking + summary≈ 300$0.000150$0.003000
One document$0.00019$0.0038
10,000 documents / month$1.92$38.40

Prices per million tokens are $0.10 / $0.50 for Haiku 5.5 and $2 / $10 for Sonnet 5.5, from LiteLLM's built-in price list as of November 2026. The same job costs 20× more on the smart model. Choosing the right model per task is model routing (Module 4).

At enterprise scale
  • Budgets are per token, not per seat. Forecast with documents × tokens per document × price, then add headroom for retries and thinking.
  • What leaves the building: every token you send goes to the vendor. Check data-retention terms, the processing region and zero-data-retention options before sending customer documents.
  • Chargeback: cost per call is the raw material for showing each team its bill (Module 2 and 3).

SECTION 3

The context window and the output limit

Explain like I'm 10

The model has a desk. Everything it reads and writes in one go must fit on the desk. Today's desks are huge, but they have edges.

Two limits apply to every call:

LimitWhat it capsWho sets itWhen you hit it
Context windowEverything the model reads: system prompt, history, documentsThe model (≈1M tokens here)An error, before any answer
Max output tokensEverything it writes, thinking includedYou, per callA cut-off answer with finish_reason="length"

A million tokens holds thousands of our invoices, so "will it fit?" is rarely the real question. Cost is, and so is attention: models miss things buried in the middle of very long prompts. Deciding what goes on the desk is context engineering (Module 8).

The output limit is the sneaky one. A cut-off answer still looks like an answer. Always check finish_reason, and leave headroom for thinking. DocuMind defaults to 2,000 output tokens.

SECTION 4

The model has no memory

Explain like I'm 10

Every request is a phone call to someone with no memory. If you want them to know something, you say it again on every call.

Tell the model a fact, then ask about it in a new request: it has no idea. Chat apps seem to remember only because they resend the whole conversation on every turn. Memory is paid for in input tokens on every message, and a long chat eventually overflows the context window.

This is the most important idea in the course. RAG (Module 7), tool calling (Module 11) and agents (Module 13) are all clever ways of deciding what to put in the next request.

SECTION 5

Same question, different answers

Explain like I'm 10

The model rolls dice each time it picks the next word, so it rarely says exactly the same thing twice.

The model picks each next token with some randomness, so one prompt gives different wording on each run. "I tried it once and it worked" proves very little. Older tutorials turned randomness down with temperature=0. Current Claude models reject that setting, and the script shows the rejection.

So where does consistency come from? From clear prompts and structured output (Module 1), and you prove it with evals (Module 9), not with a knob.

CHECKPOINT

Can you explain it?

Answer each question out loud before opening it.

A chat app "remembers" earlier messages. How, if the model is stateless?

The app resends the whole conversation with every request, so memory costs input tokens on every turn.

Why do output tokens matter more than input tokens for cost?

They cost about five times as much, and thinking is billed as output too.

The summary looks complete, but finish_reason is "length". What now?

It was cut off. Raise max_output_tokens or ask for less, and always check finish_reason.

The context window is a million tokens. Why not send every document every time?

Cost and speed grow with every token, and models miss details buried in long prompts. Send the few documents that matter (RAG, Module 7).

A teammate says "I ran it and it worked." What do you ask?

How many times, on which documents? Outputs vary per run, so you need a set of known answers and a score (Modules 1 and 9).

Glossary

token
A small piece of text (about four characters) the model reads and writes; the unit of cost.
context window
The most tokens a model can read in one request.
max output tokens
Your cap on what it may write in one request, thinking included.
finish_reason
stop: the answer finished. length: it was cut off.
stateless
The model keeps nothing between requests; the app must resend context.
LiteLLM
A library that calls every vendor through one format; Module 2's gateway.
practice mode
Canned replies, for free offline practice and tests.
